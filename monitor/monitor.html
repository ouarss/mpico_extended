Hardware

Touch sensing is done by three MPR121 capacitive controllers on the I2C bus, at addresses 0x5A, 0x5B and 0x5C. Each carries twelve electrodes, so there are 36 electrodes in total.

The playfield has 34 zones (A1–A8, B1–B8, C1–C2, D1–D8, E1–E8). Each zone is fed by one electrode; the electrode→zone assignment is the mapping (two electrodes are left unconnected, marked XX).

How detection works

Every electrode has a slowly-tracked baseline: its resting capacitance. A touch lowers the reading, so the firmware works with the delta:

delta = baseline - filtered     (never below 0)

        threshold ON  ______________________
                     |                       |
   delta rises ----->|   ON while delta >= threshold
                     |_______________________
        threshold OFF (= threshold x (1 - hyst%))
                     released once delta falls back under here
  1. Averaging — the last few frames are averaged (avg) to shed the couple of counts of noise a single frame carries.
  2. Threshold — a zone turns on when its delta reaches the zone's threshold. Higher threshold means less sensitive.
  3. Release margin (hyst) — once on, a zone stays on until the delta falls under threshold x (1 - hyst/100). This stops a finger resting at the limit from flickering on and off.
  4. Debounce — a change must hold for debounce on / debounce off frames before it is accepted, filtering out one-frame glitches.
  5. Latency — an optional extra hold, to line the input up with a slower device.

Baseline: hardware vs software

Hardware baseline uses the MPR121's own tracking. Software baseline lets the firmware track it, at a configurable rate. Tracking freezes while a zone is held, so a sustained press can never be absorbed. Set idle level (rebase) retakes the reference at once.

Timing

The control loop runs at 1 kHz. The three sensors are read one per frame (round-robin), so each refreshes about every 3 ms and the decision adds only a few milliseconds — below what is perceptible. The real limit is the MPR121's own sampling rate, not how fast the firmware reads it.

Old vs new detection

The stock Mai Pico firmware and this firmware decide a touch in fundamentally different places.

Native (stock) detection

Each MPR121 decides on its own, in hardware; the firmware only reads the chip's touched / not-touched bitmap. Sensitivity was a coarse offset (about -30 to +30) around fixed base thresholds (touch 22, release 15), nudged one step at a time with sense + / sense -. The chip tracks its own baseline and freezes it while an electrode is held.

New (software) detection

The firmware reads the MPR121 filtered value and baseline per electrode and decides itself: delta = baseline - filtered against an absolute per-zone threshold, with a release margin (hysteresis), a debounce count, optional averaging and latency, and a choice of hardware or software baseline. The MPR121 is still used, tuned as a clean front-end (gain, filter).

Native — pros and cons

  • + Simplest, lowest latency: the chip reports a press directly.
  • + Negligible I2C traffic; uses the MPR121's optimised detection.
  • - Coarse: an offset around a fixed base, no absolute per-zone value.
  • - No fine hysteresis or per-zone debounce, and no view of the noise.
  • - Hard to remove occasional spurious triggers precisely.

New — pros and cons

  • + Absolute per-zone threshold, hysteresis and debounce — set each zone just above its own noise.
  • + Live delta / baseline per zone (and the trace), so tuning is visible, not guesswork.
  • + Directly attacks the "too sensitive / false triggers" problem; the front-end (gain, filter) stays tunable.
  • - More moving parts and a little more code.
  • - Reads every electrode and decides in firmware — a few ms more latency and more bus traffic than a bare hardware flag.

Performance — is the new path fast enough?

Yes, comfortably. The loop stays at 1 kHz; the sensors are read round-robin (each about 333 Hz) and the software decision adds only a few milliseconds — imperceptible in play. Reading faster gains nothing: the MPR121's own sample rate is the real limit.

Pushing latency lower would mean flooding the shared I2C bus (it also carries the NFC reader) or shortening the chip's filters, which raises noise — the opposite of the goal. The one clean lever, if ever needed, is DMA I2C reads; today that would be premature optimisation.

In short: the native path is the leanest and lowest-latency but blunt; the new path trades a little latency and I2C traffic for fine, visible, per-zone control — the right call when the goal is to stop unwanted triggers without dulling real touches.

Avoiding false triggers

A zone that triggers untouched almost always has its threshold set below its own resting noise. The fix is to read the noise, then set the threshold just above it.

  1. Open Live and leave the glass untouched. Watch the delta of each zone: that is the resting noise floor.
  2. Note the highest resting delta a zone reaches on its own.
  3. In Tuning, set that zone's threshold a little above that figure — enough margin that noise never reaches it, low enough that a real touch clears it easily.
  4. If a zone still scintillates at the limit, raise hyst (release margin) and/or debounce.
  5. If the resting delta has drifted away from zero, press Set idle level to retake the baseline untouched.
  6. When it behaves, press Save to flash — nothing survives a power cycle until you do.

Connection

This page talks to the board over WebSerial, so it needs Chrome or Edge. Press Connect and pick the board in the browser prompt.

The Mai Pico exposes several USB interfaces. Choose the one labelled Command Line (the .2 interface) — not the game input interface. Its USB id is VID 0ca3 / PID 0021.

Once connected, the command prompt is mai_pico>. The page sends feed on automatically, which starts the live frames and makes the board republish its configuration. Use Disconnect to hand the port back cleanly before opening it in another program.

Protocol

The board emits two kinds of machine line, plus plain console text.

Live frame — F

One per frame, 74 space-separated tokens:

F  <36 filtered>  <36 delta>  <16-hex zone bitmap>

36 filtered readings then 36 delta values, one per electrode (0–35). The final token is a 64-bit bitmap of the active zones, as 16 hex characters.

Configuration — C

Emitted on feed on and after every setting change: C {json}, carrying the per-zone thresholds, the mapping, and every processing parameter (hyst, avg, latency, filter, gain, debounce, baseline mode, rate) plus the saved flag.
